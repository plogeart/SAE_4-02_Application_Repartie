1. Présentation du projet

Le projet consiste à réaliser une application répartie autour de la ville de Nancy. Le site web, hébergé sur webetu, affiche une carte Leaflet centrée sur Nancy avec plusieurs types de données : les restaurants issus d'une base Oracle, les stations VélOstan'lib et les incidents ou travaux de circulation du Grand Nancy.

L'application est composée d'un client web, d'un proxy HTTP Java, d'un service RMI Java et d'une base de données Oracle. Le proxy sert de passerelle entre le navigateur, les données ouvertes et le service RMI.

Dépôt Git : https://github.com/plogeart/SAE_4-02_Application_Repartie

2. Architecture générale

Le navigateur ne contacte pas directement tous les services externes. Il interroge le proxy HTTP Java, qui récupère les données ouvertes, appelle le service RMI et renvoie des réponses JSON exploitables par le site.

Client web HTML CSS JavaScript Leaflet

Affiche la carte, les marqueurs, les tables et les réservations. Envoie les requêtes HTTP vers le proxy.

Proxy HTTP Java HttpServer HttpClient JSON

Expose les routes /api/..., interroge les API externes, appelle le service RMI et ajoute les en-têtes CORS nécessaires au navigateur.

Service RMI restaurants Java RMI DAO JDBC

Fournit les restaurants, les tables et les réservations au format JSON. Il gère aussi la réservation d'une table.

Base de données Oracle SQL

Stocke les restaurants, les tables et les réservations. Les scripts SQL permettent de créer le schéma et les données de démonstration.

Navigateur → HTTP/JSON → Proxy Java → RMI/JSON → Service restaurants → JDBC → Oracle
Proxy Java → HTTP/JSON → Données ouvertes VélOstan'lib et incidents Grand Nancy

7. Base de données

La base Oracle contient trois tables principales :

  • RESTAURANT : nom, adresse, latitude et longitude des restaurants.
  • TABLE_RESTO : numéro de table, restaurant associé, nombre de places et statut.
  • RESERVATION : informations du client, restaurant, table, nombre de convives et téléphone.

Lors d'une réservation, le service vérifie que le restaurant existe, que la table est libre, et que le nombre de convives ne dépasse pas le nombre de places disponibles. La table passe ensuite au statut Reservee.

8. Déploiement et exécution

1. Configurer la base Oracle

Modifier db.properties avec les identifiants Oracle personnels : 

db.driver=oracle.jdbc.OracleDriver
db.url=jdbc:oracle:thin:@charlemagne.iutnc.univ-lorraine.fr:1521:infodb
db.user=LOGIN
db.password=MDP

2. Initialiser les tables

sql/schema.sql
sql/demo-data.sql

3. Compiler le projet

ant clean compile

4. Lancer le service RMI

./scripts/start-rmi.sh

5. Lancer le proxy HTTP

./scripts/start-proxy.sh

6. Configurer le site web

Dans site/js/config.js, adapter l'URL du proxy si les services sont lancés sur une autre machine : 

window.APP_CONFIG = {
    API_BASE_URL: "http://localhost:8000"
};

Pour la démonstration, il faut remplacer localhost par le nom ou l'adresse de la machine qui exécute le proxy. Les adresses ne sont donc pas codées directement dans le JavaScript principal.

9. Tests possibles pendant la démonstration

Les routes suivantes permettent de vérifier rapidement que les services répondent : 

curl http://localhost:8000/api/health
curl http://localhost:8000/api/restaurants
curl http://localhost:8000/api/tables
curl http://localhost:8000/api/velos
curl http://localhost:8000/api/incidents
curl http://localhost:8000/api/reservations

Côté navigateur, la console de développement permet aussi de vérifier les erreurs réseau, les erreurs CORS ou les réponses JSON incorrectes.

10. Gestion des problèmes réseau

  • Le proxy vérifie les codes de réponse HTTP des API externes.
  • Les erreurs sont renvoyées au format JSON avec success: false et un message explicite.
  • Le site affiche des messages d'erreur lorsqu'une ressource ne peut pas être chargée.
  • Les données vélos et incidents sont mises en cache temporairement côté proxy pour limiter les appels externes.
  • Les fichiers de configuration permettent d'adapter les hôtes, ports et URLs sans modifier le code principal.

11. Sécurité et contournement CORS

Certaines données ne peuvent pas être récupérées directement depuis le navigateur à cause de la politique de sécurité CORS. Le proxy permet de contourner ce blocage dans le cadre de la SAÉ, car c'est le serveur Java qui interroge les données externes, puis qui renvoie une réponse au navigateur.

Ce contournement doit rester contrôlé. Dans un vrai projet, il faudrait vérifier les sources appelées, limiter les routes exposées, éviter de créer un proxy ouvert vers n'importe quelle URL, contrôler les entrées utilisateur et configurer précisément les origines autorisées au lieu d'utiliser systématiquement Access-Control-Allow-Origin: *.

12. Points importants pour la soutenance

  • Le site web doit être hébergé sur webetu.
  • Le serveur RMI et le proxy doivent être lancés sur des machines de la salle.
  • Le service RMI doit être lancé avant le proxy, car le proxy recherche le service RMI au démarrage.
  • Le fichier site/js/config.js doit pointer vers la machine qui lance le proxy.
  • La base Oracle doit être initialisée avant la démonstration.
  • Chaque membre de l'équipe doit pouvoir expliquer une partie : site web, proxy, RMI, base de données ou déploiement.

14. Résumé

Le projet répond au principe d'une application répartie : le navigateur affiche les informations, le proxy centralise les appels réseau, le service RMI fournit l'accès métier aux restaurants, et la base Oracle stocke les données persistantes. Les échanges entre les composants se font principalement en JSON, ce qui simplifie l'intégration entre le JavaScript du site, le proxy Java et le service RMI.
